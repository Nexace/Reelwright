## 1. Licence (exact, read this first)

Text read from `remotion/LICENSE.md` (repo root, "Copyright © 2026 Remotion"):
- **Free License** if you are: an individual; a for-profit organization with up to 3 employees; a non-profit or not-for-profit organization; or evaluating Remotion and not yet using it commercially.
- **Allowed**: use it, non-commercially or commercially, "for the purpose of creating videos and images", and modify it "for the purpose of fulfilling their custom use case or to contribute bug fixes or improvements back".
- **Disallowed**: "copy or modify Remotion code for the purpose of selling, renting, licensing, relicensing, or sublicensing your own derivate of Remotion."
- **Company License** required for everyone else (for-profit "of a certain size"), bought at remotion.pro/license. Same software, no feature difference; adds prioritized support.
- The file's header says: "In Remotion 5.0, the license will slightly change" (PR #3750, still open: contractors count toward team size; the company license becomes bound to the new Terms).
- NOT open source: `npm view` shows `SEE LICENSE IN LICENSE.md` for remotion/@remotion/cli/renderer/lottie/gif/google-fonts, `UNLICENSED` for @remotion/transitions and @remotion/effects (read as Remotion License; UNVERIFIED how they intend it), `Remotion License` for light-leaks/starburst/mac-cursors, `See LICENSE.md` for rive. Remotion's own FAQ: "source-available ... not open source".

Docs at 4.0.540 (`docs/license/faq.mdx`, `docs/terms.mdx` = Terms v5.0, marked "Upcoming", effective with Remotion 5.0; the v4 terms page at remotion.pro/terms-4-0 I fetched says it is outdated and says nothing on pricing/eligibility, so which wording binds a 4.0.540 user is UNVERIFIED):
- Free definition there: "an organization or team of individuals with up to 3 people" (total headcount incl. contractors), non-profit definition is narrow (needs evidence; governments, schools, trade bodies do not qualify).
- Company License options: **Creators** $25 per seat per month, no minimum ("a single person either writes Remotion code themselves or leverages agentic coding tools such as Claude Code, Codex, OpenCode"); **Automators** $0.01 per render, $100/month minimum, for anyone "owning code that programmatically calls" `renderMedia()`, `renderStill()`, `renderFrames()`, `npx remotion render`, `npx remotion still`, Lambda/Cloud Run/Vercel/web render APIs, or using `<Player>`. Enterprise: min $500/month. Previews in Studio/Player are not renders. Local-only deployment "does not require the purchase of Renders" (Terms, Server-side rendering).
- Free users may automate and embed the Player with no render purchase. "There is no difference in functionality."
- Agency rule: if you only hand a client the finished mp4, only the agency's headcount counts. If the client owns/operates the Remotion project, headcounts aggregate.
- Rendering service rule: allowed to let users change parameters of hosted Remotion code or to generate Remotion code with AI; NOT allowed to let end-users bring/upload their own Remotion code. Terms v5.0 also say: whoever provides "functionality allowing end-users to download a Remotion project or code" must make the exported code "clearly indicate it is built with Remotion and include a link" to remotion.pro/license.
- Telemetry (4.0.540): server-side sends nothing unless you pass a `--license-key` (the CLI rejects any key not starting `rm_sec_`); client-side render (`@remotion/web-renderer`) always reports. Remotion 5.0 (`5-0-migration.mdx`, "not yet released"): telemetry mandatory for Automators; free users pass the literal key `"free-license"`; WebGL default changes to `angle`; `selectComposition()`/`getCompositions()` require `inputProps`.
- Codec patents are not covered by a Remotion licence (FAQ). Remotion ships an FFmpeg binary under GPLv2+ (`docs/miscellaneous/ffmpeg-license.mdx`; x264/x265 are GPL) inside `@remotion/compositor-*`.
- Product prices seen: Editor Starter $600; Timeline component paid (price not stated in the docs read).

What Reelwright must tell users, and how it stays MIT-clean:
1. Reelwright does not bundle, vendor or redistribute Remotion. The renderer is opt-in; the user installs Remotion themselves (`npm i` in their project, never in the repo root, never in `vendor/`, never committed). That keeps the MIT repo free of the Remotion licence (a copy would be "Remotion code" under a non-MIT licence).
2. Setup text and README must say, in plain words: "Remotion is not open source. It is free for individuals, for-profit companies with up to 3 people, and non-profits; every other company needs a paid Company License (remotion.pro/license; currently $25 per creator per month, or $0.01 per render with a $100 monthly minimum for automated pipelines). Using `renderer: remotion` makes YOU a Remotion user. Reelwright is not affiliated with Remotion and does not grant a Remotion licence. Check remotion.dev/docs/license." Show it once on `new --renderer remotion` and in `setup --with-remotion`, and require typing a yes (an explicit acknowledgement; no silent install).
3. Do not set a license key or telemetry anywhere; do not call it free for everyone. Say that a company with 4+ people running `reelwright all` with this renderer is "owning code that calls `npx remotion render`", so the Automators plan, not only Creators, is the likely fit (their reading, not legal advice).
4. The scaffold written into `<project>/rm/` should carry a comment and README line "built with Remotion, see remotion.pro/license" (Terms v5.0 download-attribution rule; harmless now).
5. Reelwright must not become a service that renders other people's uploaded Remotion code (e.g. a hosted Reelwright). Local CLI use is fine.
6. The MIT sub-packages (see rows) are the only Remotion-published code we could ever vendor: `@remotion/paths`, `@remotion/shapes` (make* functions), `@remotion/media-utils` have a real MIT `LICENSE.md` ("Copyright (c) JonnyBurger", read). `@remotion/noise`, `captions`, `layout-utils` say `"license": "MIT"` in package.json but their published tarballs contain no LICENSE file (tested with `npm pack`), so prefer rewriting. The skills repo (remotion-dev/skills) has no licence at all (Phase 9, GitHub license API 404): never copy its text or examples.

## 3. Design: the optional Remotion renderer (`"renderer": "remotion"`)

### 3.1 How a project opts in
- `./video.sh new my-film --renderer remotion` copies a template (`tools/templates/remotion/`, to add) into `projects/my-film/rm/` and sets `"renderer": "remotion"` in project.json. Needs a new `tools/renderers/remotion.mjs` (default export `(DIR, P, mode, extra)` per the contract at the top of tools/render.mjs; `render.mjs` already resolves `tools/renderers/<name>.mjs`, so no core change) plus `FRAME.remotion` in tools/manifest.mjs and a `renderer === "remotion"` branch in tools/qa.py/qa_page.mjs.
- Nothing is installed by default. `node setup.mjs --with-remotion` (or the first `new --renderer remotion`) prints the licence notice (section 1), asks for a yes, then runs inside `projects/<name>/rm/`: `npm i` (pinned exact versions) and `npx remotion browser ensure`. Project-local `node_modules`, so root `package.json`, `vendor/` and CI stay Remotion-free. `reelwright smoke` gets a Remotion line that renders one frame.
- Template files (all MIT, ours): `rm/package.json`, `rm/src/index.js` (`registerRoot`), `rm/src/Root.jsx` (`<Composition>` with `calculateMetadata` from kit data), `rm/src/Film.jsx` (the edit), `rm/src/kit.js` (timing bridge), `rm/public/` (symlink or copy of `vo/`, `fonts/`, `assets/`, `theme.css`), `rm/remotion.config.js`, README with the licence line.

### 3.2 Install cost (tested on macOS arm64, Node 24.22, 2026-11-05)
- npm: `remotion@4.0.540 @remotion/cli@4.0.540 react@19 react-dom@19` = 244 packages, 36 s, 246 MB `node_modules` (largest: @remotion 65 MB, @rspack 44 MB, @babel 38 MB, @remotion/studio 20 MB, compositor-darwin-arm64 18 MB incl. its own ffmpeg/ffprobe).
- Chrome: `remotion browser ensure` downloads Chrome Headless Shell (140.3 MB download from remotion.media, about 459 MB on disk in `node_modules/.remotion/`). Chromium 158.0.8127.2.
- Each extra package (`@remotion/transitions` 0.5 MB unpacked, `effects`, `three`, `lottie`...) is small. Total about 0.7 GB, 5 minutes. Needs internet once; after that renders offline (verified: no licence prompt, no network use seen in a verbose render log).
- Cheaper option (tested on one trivial film): `--browser-executable <Playwright headless shell>` gave byte-identical frames, so the Chrome download can be skipped when the film uses no HTML-in-canvas / WebGL effects. Remotion's skill says not to; effects/shader transitions are UNVERIFIED on Playwright's build.
- Min Node: UNVERIFIED (docs use a `<MinNodeVersion/>` component I did not resolve); worked on Node 24.

### 3.3 How kit data reaches a composition (and render(t) purity)
- `sched.py` already writes `film/data.js` / `hf/kit-data.js` as `window.VO`, `window.MUSIC`, `window.PROJECT`. Add one more output, `rm/kit-data.json` (same content as JSON: `{project:{fps,lead,tail,speechEnd,width,height}, vo:{id:{start,end,text,words:[{w,t,d}]}}, music:{beat,bar,t0,drop,...}}`), written by the same code (S).
- Renderer passes it with `--props=kit-data.json` (tested: file path works, values arrive as component props and as `calculateMetadata({props})`). `calculateMetadata` returns `durationInFrames = ceil(DUR * fps)` and `fps`, so the film length is never hard-coded.
- `rm/src/kit.js` = a pure subset of tools/engine.js: `clamp/seg/lerp/E/easing/bezier/spring/keys/stagger/local/win`, `beat/bar/snap/pulse/drop`, `V/W/WE/align/words`, `fmt/safe/u`. Today engine.js binds to `window.VO` and the DOM at load; refactor its pure half into `tools/kit-core.js` (UMD) that takes `(VO, MUSIC, size)` and is used by engine.js, by `kit.js`, and by Node-side checks (M). Then `useKit()` = `{t: frame / fps, ...core}`.
- A film is `const Film = (props) => { const k = useKit(props); const t = k.t; ...; return <AbsoluteFill>...</AbsoluteFill> }`. Every timing is `k.W('hook','code')` or `k.snap()` (seconds); frames only appear at the very edge, `f = t * fps`, so the same numbers drive pvk, HyperFrames and Remotion. Cue list and duration live in `rm/src/film.mjs` as plain ESM (no JSX) so `info` can import it in Node: `export const cues = (kit) => [...]`, `export const DUR = (kit) => ...`, and `Film.jsx` imports the same functions.
- Rules carried over: no `Date.now`, `Math.random`, timers, CSS transition/animation, Tailwind `animate-*`/`transition-*`, no `useFrame` from R3F; use `random('seed')`. `qa.py` "seekable" gate: scan `rm/src/**` with the same regex list (+ `useFrame`, `animate-`) (S).

### 3.4 Frame-accurate determinism
- Remotion's model equals ours (`flickering.mdx`: tabs share no state, everything is a function of `useCurrentFrame()`; renderer waits for `window.remotion_renderReady` after `remotion_setFrame`). Frame f is exactly t = f/fps.
- Tested: 90 frames, PNG: `--concurrency=1` vs default gave identical SHA-256 for all 90 frames; frame 27 at 30 fps shows t = 0.900. The same frames with Playwright's headless shell also matched (0 of 90 differ). `--frames 15-44` encodes exactly 30 frames (ffprobe). Not tested: video layers, WebGL effects, fonts across OS, Windows.
- `verify` then works unchanged on `frames/` plus manifest (add the remotion and Chrome versions to the tools block).

### 3.5 Plugging into Reelwright's mix / encode / qa / verify
- `info`: Node-import `rm/src/film.mjs` -> `timeline.json {DUR, cues, VO}`.
- `stills t,t,..`: `npx remotion render src/index.js Film out --sequence --image-format=jpeg --props=kit-data.json --frames=<f1,f2,..>` (comma list tested; files are `element-<frame>.jpeg`, rename to `stills/t<time>.jpg`). Faster than pvk's "render whole film at 10 fps".
- `frames`: `--sequence --image-format=png --image-sequence-pattern='frame_[frame].[ext]' --concurrency=<PAGES> --muted` into `frames/` (tested). Always full render (like HyperFrames; no fingerprint cache); `--frames a-b` for partial renders. Use `--width/--height/--fps` from `--formats`, so `KIT.fmt` becomes `useVideoConfig()`.
- `encode`: reuse `encode()` from tools/renderers/pvk.mjs exactly as hyperframes.mjs does (frames + `mix.wav` + subtitles). Reelwright keeps owning audio: `--muted` stops Remotion mixing, so `mix.py` (VO, ducked music, SFX, loudnorm -14 LUFS, true peak gate) stays the single source. Trade-off: Remotion `<Audio>` components in film code are ignored in this mode; per-clip volume curves must go through the planned `K.audio` -> mix.py layer. An opt-in `"audio": "remotion"` could let Remotion mix and then loudnorm in ffmpeg, but loses ducking; not recommended.
- `qa`: frame-based checks (blank, jumps, loudness, flash, dark) work as is on `frames/`. Page-based gates (captions, illustrative, ai-label, overlap, tiny-text, wordy: tools/qa_page.mjs opens the film page and seeks `window.render(t)`) need a page: proposal = a Reelwright-owned host page that mounts the same `Film` with `@remotion/player` and exposes `window.render = (t) => player.seekTo(Math.round(t*fps))`. UNVERIFIED (not prototyped). Until it exists, print "SKIP (renderer remotion)" for those gates and WARN, never silently pass.
- `preview`: spawn `npx remotion studio --port 4174` (they document `--no-open`, `--port`, `--force-new`) and print the URL; mix waveform view stays pvk/HF only.
- `verify`/manifest: `FRAME.remotion = /^frame_\d+\.png$/`, record `remotion` and Chrome build, hashes as today. Cross-OS differences: see docs/REPRODUCIBLE.md (same caveats, plus Remotion's Chrome build differs from Playwright's).
- Themes: `theme.mjs` writes `theme.css` into the page dir; for Remotion write it to `rm/public/theme.css` and load it with a `<link>` or inline `<style>` plus `@remotion/fonts` `loadFont` on bundled `fonts/` (waits via `delayRender`).
- Languages: `--lang es` regenerates kit-data.json from `langs.es`; props change, film does not.

### 3.6 Windows
- Remotion supports Windows x64 (`chrome-headless-shell.mdx`: "macOS (x64 and arm64), Windows (x64), Linux (x64 and arm64)"; npm has `@remotion/compositor-win32-x64-msvc` 4.0.540, os win32 cpu x64). No Windows arm64 package exists (not in `packages/` listing): say so in setup.

### 3.7 Free from the Remotion renderer vs also build natively

Free with `renderer: remotion` (React films): TransitionSeries with 21 presentations (12 of them HTML-in-canvas shaders), `@remotion/effects` (about 90 GPU effects, LUT/curves/levels), HTML-in-canvas, motion blur (3 kinds), `<Video>`/`<OffthreadVideo>` frame-exact footage with trim/rate/loop, Lottie, Three.js/R3F, Skia, Rive, `<AnimatedImage>`/`<Gif>`, rough-notation, shapes, noise, paths, captions utilities, Studio with props editor and interactivity, Player, codecs (h265, vp9, av1, ProRes 4444, WebM alpha, GIF), hardware encode, Zod props.

4. Encode options: codec presets (h265, vp9, av1, ProRes, GIF), crf/preset/bitrate/pix_fmt, hardware encode, alpha (transparent) output, mp4 metadata. (M)
5. Parameterised renders `--props`/batch + schema. (M)

## 4. Integration notes (summary)
- Both Remotion and Reelwright are "paint frame f, wait, screenshot" engines; `render(t)` -> `f / fps` is lossless, so the bridge is thin (tested end to end with kit-style word times and beats as props).
- Easiest and most robust bridge: Reelwright calls the Remotion CLI and takes an image sequence; mix, encode, manifest, qa frame checks stay ours. Avoid Remotion's own encoder/audio so loudness and ducking behave identically in all three renderers.
- Authoring cost is the real price: Remotion films are React (JSX, bundling), pvk/HF films are imperative DOM. The shared pure core (`kit-core.js`) is what keeps timing identical.
- Formats: `--width/--height/--fps` per `--formats` entry (flags exist); audio built once.

## 5. Risks
1. Licence: Reelwright users in companies of 4+ people owe Remotion money the moment they use this renderer; wrong or buried messaging would be a real harm and a reputational issue. Terms v5.0 (not yet in force) tighten telemetry/contractor rules; 4.0.540's binding terms text I could not read (v4 page is outdated and silent). Re-check both when Remotion 5.0 ships.
2. Remotion can change licence/pricing (their Terms allow fee changes), and "Free" thresholds differ between LICENSE.md ("up to 3 employees") and the docs FAQ ("up to 3 people", includes contractors).
3. No licence on remotion-dev/skills: no copying; also `@remotion/effects` and `@remotion/transitions` are `UNLICENSED` in npm metadata (ambiguous), so never vendor.
4. GPLv2+ FFmpeg binary comes with `@remotion/compositor-*`; fine when installed by the user, a problem if Reelwright ever ships it.
5. Weight: about 0.7 GB, 5 minutes, internet needed once. Version lockstep: every `@remotion/*` must be the exact same version (skills `upgrade`), and Lambda-free.
6. Shader presentations, effects, HTML-in-canvas need Remotion's own Chrome build (Chrome 149+ flag otherwise) and `--gl=angle` (default only in 5.0); not portable to pvk/HF; results differ across GPUs: UNVERIFIED for determinism (software GL on CI would be needed).
7. QA parity: page-based gates need the Player-host page (UNVERIFIED); until then they are skipped.
8. Determinism proven only on a trivial text film on one machine; video layers (`<Video>` WebCodecs vs OffthreadVideo fallback), fonts across OS, WebGL and Windows untested.
9. Windows arm64 unsupported by Remotion; macOS Intel needs `compositor-darwin-x64` (exists).
10. Our docs must not say "Remotion-compatible"; do not imply endorsement (Terms: no implied qualified relationship with Remotion).
11. skills content has features changing fast (Interactive.*, effects, HtmlInCanvas appeared in the last few 4.0.5xx releases): pin the version and re-audit before each Reelwright release.
